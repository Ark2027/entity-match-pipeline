# Does an LLM improve the matcher?

Short answer: yes, on the cases it was given, and the more useful findings came from the two bugs the evaluation exposed along the way.

Model: `claude-sonnet-5`. Fixtures and ground truth are in `fixtures/`, generated by `scripts/generate_fixtures.py`. Reproduce with:

```bash
python scripts/generate_fixtures.py
python run_matcher.py --config config/settings.demo.json --quarter 2026Q2 --rebuild-history
python eval/run_eval.py                # deterministic baseline
python eval/run_adjudication.py        # with the LLM, needs ANTHROPIC_API_KEY
```

## Setup

The deterministic matcher sorts every record into auto-accepted, deferred, or discarded. The LLM only ever sees the deferred band. It cannot touch an auto-accept and cannot resurrect a discard, so it can add automation but cannot damage decisions that were already made.

92 labelled records. 84 have a correct answer; 8 are traps where the correct answer is "none of these", included specifically to see whether a model asked to find a match will invent one.

## Results

| | v1 deterministic | v2 with adjudication |
|---|---|---|
| automated decisions | 80 | **84** |
| deferred to a human | 8 | **4** |
| automation rate | 95.2% | **100%** |
| automation precision | 100% | **100%** |
| error rate | 0% | **0%** |
| trap survival | 100% | **100%** |

The LLM resolved 4 of the 8 deferrals, all correctly, and declined the other 4 — which were the traps. Every record with a correct answer is now handled automatically, and nothing that should have stayed unresolved was resolved.

**Cost:** $0.0575 for 8 adjudications, about **$0.007 each**, at 2.5s average latency. On this workload the LLM runs on roughly 8% of records, so per-record cost across the whole run is under a tenth of a cent.

## What it actually solved

The deferrals were all one pattern: `NW Ironwood Supply Co` against candidates `Northwest Ironwood Supply` and `Northwest Iron Works`. Both share a prefix; only one is the same business. String distance cannot break that tie because the decoy is lexically closer to the query than to the answer in some variants.

The model's reasoning, verbatim:

> "NW" expands to "Northwest" and "Ironwood Supply" matches distinctively with "Northwest Ironwood Supply"; same state, amount falls within size band, and lead date precedes reported date, all corroborating a match.

And on a trap:

> "Blue Ridge" is a common geographic descriptor shared with candidates, but the distinctive business type words (Tannery vs Upholstery, Roofing, Bakery) differ entirely. No candidate shares the core distinctive identifier "Tannery".

That second one is the behaviour worth having. It is the same reasoning the deterministic stopword guard implements by hand, arrived at independently.

## The two bugs this found

### 1. A tool schema that invited contradiction

The first version of the schema had both a `decision` enum (`match` / `no_match`) and a nullable `candidate_application_id`. Two fields encoding one fact.

The model returned only the id and omitted the enum, despite it being listed as required. The parser read the missing key as a refusal. **Every single adjudication came back "no match" while the `reasoning` field argued the opposite** — the run looked plausible, reported zero improvement, and was entirely an artifact of my schema.

Two changes came out of it: the schema now has one field carrying the decision, with `0` meaning no match; and a missing required field raises an error rather than silently falling through to a default. Both are in `llm_adjudicator.py` with the reasoning kept in comments.

The diagnostic that cracked it was the `reasoning` string. Had the tool only returned a decision, this would have looked like a model that refused everything.

### 2. Ground truth that contradicted itself

The first clean run reported a **1.2% error rate** — one wrong automated decision. Chasing it found the fixture generator had produced the same business name twice within one source and state, each expecting a different candidate. Two identical records that must map to different answers is not a hard case, it is an unanswerable one, and it surfaced as a model error rather than a broken fixture.

`run_eval.py` now refuses to score ground truth containing duplicate keys, and the generator excludes collisions.

Fixing it also **raised the deterministic baseline** from 84.5% to 95.2%, because those colliding names were generating spurious deferrals. Nine of the seventeen original deferrals were an artifact of the test data.

## What I would not claim

**The eval is small.** 8 deferrals, and they reduce to 2 distinct scenarios repeated once per source. A perfect score on 2 scenarios is encouraging, not conclusive.

**A perfect result usually means the test is too easy.** The honest read is that the deterministic matcher already handles almost everything, and the residual is a narrow band the model happens to be well suited to. Three of the four case types I designed as "genuinely ambiguous" were resolved by the deterministic scorer without help — I was wrong about what would be hard.

**No adversarial testing.** Nothing here probes prompt injection through a business name, degenerate inputs, or what happens when all candidates are plausible.

**Single model, single run.** No temperature sweep, no comparison against other models, no repeat runs to measure variance. The 100% could move on a re-run and I have not measured that.

## What I would do next

- Repeat runs to measure variance rather than reporting one sample.
- A harder fixture set, built by looking at which real-world cases actually get deferred rather than guessing.
- Compare against a cheaper model, since this task may not need a mid-tier one.
- Test business names containing instructions, since they flow straight into the prompt.
- Measure whether the confidence field predicts correctness well enough to lower the gate from `high` to `medium`.
